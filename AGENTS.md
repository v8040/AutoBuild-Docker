# AGENTS.md

## Repo purpose

Docker image build repo. Each subdirectory (`bentopdf`, `derper`, `jupyterhub`, `jupyterlab`, `sharelatex`) holds a `Dockerfile`; compose files are examples only. `derper` is a standalone binary, so it has no Dockerfile. `.github/runner` holds the self-hosted Actions runner image, built manually with compose and excluded from the build matrix. `images.txt` also lists external images (smartdns, sing-box, home-assistant) for mirroring only

## Build and CI

- All builds are manual, triggered via `workflow_dispatch` in `.github/workflows/build.yml`; there are no push or PR triggers
- Only the repo owner can trigger builds (owner-only guard in the workflow)
- `build.yml` selects a single project or `all`. The `all` matrix discovers Dockerfiles at depth 2, so `.github/runner` is excluded
- Both workflows keep 2 days of run history

## Known workarounds

- **jupyterlab python pin**: `jupyterlab/Dockerfile` overwrites `conda-meta/pinned` with the base image's exact python version before `mamba update -aqy`. `mamba update --all` triggers a full environment reinstall when python changes, docker-stacks images ship without `/opt/conda/pkgs`, and micromamba cannot fetch packages for reinstall actions, so relinking fails with `Cannot find a valid extracted directory cache`. Remove the pin once mamba-org/mamba handles reinstall on cacheless environments

## Runner

- `runner.env` is generated by an external deploy script into `.github/runner/runner.env` and added to `.git/info/exclude`; never commit it
- Required `REPO_URL` `GH_PAT`, optional `RUNNER_NAME` `LABELS` `RUNNER_WORKDIR`. The script also sets `ACTIONS_RUNNER_PRINT_LOG_TO_STDOUT=false`
- Defaults: `RUNNER_NAME=tcr-runner`, `LABELS=tcr-sync`
- The deploy script must point its `BRANCH` at the branch that owns `.github/runner`; after merge that is `main`

## Platform support

- `sharelatex` is **linux/amd64 only** (TeX Live `scheme-full` doesn't install cleanly on arm64)
- All other images build for `linux/amd64,linux/arm64`

## Build-time dependencies (not in repo)

- **jupyterlab**: clones oh-my-bash, oh-my-zsh, zsh-syntax-highlighting, zsh-autosuggestions; downloads a jovyan tarball from a secret URL (`URL_JOVYAN`). COPY instructions reference `opt/` and `jovyan/`
- **sharelatex**: downloads a fonts tarball from a secret URL (`URL_FONTS`). COPY references `custom/`
- **bentopdf**: all downloads happen inside the Dockerfile, with no workflow fetch step or secrets. CDN references are rewritten to same-origin `/wasm/`, tesseract.js uses a same-origin worker, and Noto CJK fonts are injected into the embedded LibreOffice data blob for CJK Word-to-PDF. The embedded docs site is inert and exempt from residual-external-reference assertions
- **derper**: no external dependencies

## Registries

Images are pushed to Docker Hub (`docker.io/v8040/<project>`) and GHCR (`ghcr.io/v8040/<project>`)

## Mirroring (sync.yml)

`images.txt` lists images to sync to Tencent Cloud TCR (`ccr.ccs.tencentyun.com`). Each line is `<source_image> [target_name]`; lines starting with `#` are ignored. The workflow uses `skopeo copy` and prefers the GHCR mirror when available. Auth is resolved from `$DOCKER_CONFIG` or `~/.docker/config.json` in the shared "Set Auth" step. Deduplication is by target image name. The `runner` input defaults to `github-hosted`; select `self-hosted` to run on the `tcr-sync` runner

## Code conventions

- Use `jq` for JSON manipulation, never `sed`/`grep` for structured data
- Runners have `jq` and `curl` pre-installed

## Secrets required

**Build**: `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`, `URL_JOVYAN`, `URL_FONTS`

**Sync**: `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`, `TCR_USERNAME`, `TCR_TOKEN`, `TCR_NAMESPACE`, `IMAGE_LIST_URL`
